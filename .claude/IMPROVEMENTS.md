# Improvements

- 2026-08-15 frontend/app: six pages still overflow horizontally at a 390px viewport after `main` gained `min-w-0` — player-overview, match-history, matchmaking-analysis, playstyle-analysis, tracked-players and my-profile all report document scrollWidth 476 against clientWidth 390, and match-history reports 1281. The container is correctly constrained to 390; a descendant is ~460 wide with no scroll container of its own, so the content overflows visibly. Pre-existing and unrelated to LGA-21; measured with a per-route sweep. **2026-08-16: could not reproduce against an empty local database.** All six routes were loaded authenticated at a true 390px viewport (agent-browser `set viewport`) and every one reported scrollWidth 390 with zero overflow — but with no players or matches stored, none of the wide descendants render at all (`table tbody tr` count 0), so this is an inconclusive run rather than a fix. Reproducing it needs seeded player data: either a Riot-backed local fetch or the anonymised production mirror.
- 2026-08-16 backend/app/core/riot_api/credential_health.py: `RiotAPIKey.times_used` is dead — no code path ever increments it (all 27 production rows sit at 0), and `last_used_at` is only written at settings-validation time, never by real request traffic. Either wire increments into the client/rate limiter or drop both columns.
- 2026-08-16 backend/app/features/matches/models.py, backend/app/features/players/models.py: the constraint-name doubling already shipped to production. `core.matches` holds `ck_matches_ck_matches_platform_is_lowercase` and `core.players` holds `ck_players_ck_players_platform_is_lowercase`, both created by revision `20260816_0012`, which passed a name that already carried the `ck_<table>_` prefix into the `ck_%(table_name)s_%(constraint_name)s` convention. The drift gate cannot see it because the models spell the doubled name too, so model and database agree — on a wrong name. Cosmetic only (the constraints work), but fixing it needs a migration that renames both, not just a model edit.
- 2026-08-16 backend/pyproject.toml: `reportUnnecessaryIsInstance` and `reportUnnecessaryComparison` are disabled on a justification that no longer holds. They were turned off because the ORM annotations were more confident than the schema; revision `20260816_0014` closed that gap and `alembic check` runs clean. Re-enabling them reports every defensive guard in the codebase at once, so each needs judging on whether it defends against malformed Riot payloads or against a lying annotation. `app/features/players/service.py` carries the same suppression for `game_name`/`tag_line`.
- 2026-08-16 backend/alembic/env.py: two schema differences stay outside `alembic check` even now that it is the gate. (1) `compare_server_default` is off; turning it on reports **128 diffs, measured**, every one of them "the database has a `DEFAULT` and the model declares only a client-side `default=`" — real drift in the sense that a raw `INSERT` and an ORM `INSERT` disagree, but closing it means auditing 128 columns for which side is right, not flipping a flag. (2) CHECK constraints are compared by name only (Alembic's `checkconstraint_byname` plugin), so editing a constraint's expression while keeping its name passes. Both are pre-existing and were confirmed still open by the 2026-08-16 review; neither is a regression from the reconciliation.
- 2026-08-16 frontend/features/players/components/add-tracked-player.tsx: dead component — exported from features/players/index.ts but no page renders it (frontend/app/tracked-players redirects to player-overview); its kind-specific error toasts (invalid Riot key, rate limit) are unreachable, only unit tests exercise them.
- 2026-08-16 frontend/components/ui/card.tsx: CardTitle renders h3, but six call sites put buttons/badges/block content inside it (job-card.tsx:637 and others) — invalid content model and screen readers announce whole cards as headings. Needs the heading scoped to the text span or an asChild escape hatch. Only job-card.tsx has interactive controls inside the heading; the other five are Badge-only.
- 2026-08-16 frontend/components/providers.tsx: the global QueryCache error toast double-reports on surfaces that already render inline query errors (match-history, smurf-boost-detection); meta.silenceErrorToast exists but has zero call sites.
- 2026-08-16 frontend/tests/dialog-contract.test.ts: the dialog-white-border rule is enforced by fragile regex source-scanning; making the class the default inside DialogContent's cn() would be zero-visual-change and unbreakable.
- 2026-08-16 frontend/features/players/player-query.ts: query functions rethrow `new Error(result.error.message)`, stripping the normalized ApiError's code/status/kind — queryErrorToast then classifies every failure as "unexpected" and always shows the generic fallback description, so curated backend messages (404s etc.) never reach the viewer through the QueryCache toast. Same root cause as the lib/core/api.ts entry below.
- 2026-08-17 frontend/lib/core/api.ts: validated* helpers resolve `{success:false}` instead of throwing, so a query that only reads `.data` silently bypasses the QueryCache error-toast contract documented in frontend/CLAUDE.md; ~16 call sites compensate with `throw new Error(result.error.message)`, flattening the structured error kind. Either throw from the helpers or give call sites a shared unwrap that preserves the kind.
- 2026-08-17 frontend/features: six endpoint functions still call raw axios (`api.get<...>`) instead of the validated* wrappers after the d6fcbb2 extraction converted trackPlayer only — no runtime validation on those responses. Convert for consistency.
- 2026-08-17 frontend/features/settings/components/account-settings-card.tsx: re-parses API error detail by hand where lib/core/api-error already centralizes it (moved verbatim from the old settings page); duplication only, no security issue.
- 2026-08-17 backend/app/features/players/router.py: add-tracked onboarding sync inherits run_player_sync's already-running gate — if the fleet-wide Match Fetcher is mid-run, the onboarding run records SYNC_BUSY and the player waits for the next scheduler pass, while track-player-button.tsx toasts unconditional success off the 200. The data self-heals; the UX could watch the run via usePlayerSyncRun and say "queued behind the current update" instead.
